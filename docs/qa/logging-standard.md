# Seal 运行日志规范

## 目标

日志要让开发者回答四个问题：用户执行了什么、程序走了哪条路径、在哪个阶段失败、失败后做了什么。日志是本地排障材料，不是点击统计或遥测；Seal 不应因本规范自动上传日志。

## 记录边界

### 必须记录

- 一次有业务结果的操作开始与结束：IPA 导入、签名、安装、续签、账号验证、设备配对、更新、数据清理、日志导出。
- 影响后续路径的判定：例如选择描述文件续签或完整重签，并记录可审计的判定原因。
- 关键阶段切换、重试、取消、跳过与恢复结果；后台或快捷指令触发时，记录触发来源及未执行原因。
- Apple、文件系统、设备安装通道等外部边界的操作名称、耗时、结果类别、重试次数，以及安全脱敏后的错误域/错误码。
- 失败的稳定 `SEAL-*` 错误码、脱敏底层原因，以及用户恢复动作是否成功。

### 不记录

- 页面打开/关闭、导航、普通按钮点击、视图刷新、输入字符和表单原文。
- 高频进度回调、轮询每一轮、重复的相同状态通知。只记录开始、阶段摘要、异常阈值和最终结果；轮询结束时可汇总次数与总耗时。
- Apple ID、密码、验证码、认证票据、P12/私钥、配对文件内容、完整 UDID、完整证书序列号、完整请求 URL、原始请求/响应体和无必要的绝对路径。

因此规则是：记录**有业务语义的操作与状态变化**，不记录每次 UI 点击。用户取消一项已经开始的长操作需要留痕；打开页面后什么也没做不需要留痕。

## 每条事件的字段

新日志按以下字段设计；没有值的字段省略，不用猜测值：

| 字段 | 用途 |
| --- | --- |
| 时间 | 北京时间，精确到秒；耗时用毫秒或秒单独记录，不从两条日志的时间差猜 |
| 构建 | 营销版本与 CI 构建号，放在导出文件头 |
| 类别 / 级别 | 账号、配对、签名、安装、续签、系统；信息、警告、错误 |
| 操作 / 触发来源 | `importIPA`、`sign`、`renew`、`batchRenew`、`install` 等；手动、启动、后台、快捷指令 |
| 关联 ID | 多阶段操作共享同一个随机 `operationID`；单次失败共享 `diagnosticID`，便于从错误卡片定位完整日志 |
| 阶段 / 结果 | 稳定阶段名，以及 `started`、`succeeded`、`failed`、`cancelled`、`skipped` 等明确结果 |
| 错误信息 | 稳定错误码、来源模块、底层域/码、脱敏原因和已尝试的恢复动作 |
| 安全上下文 | 仅记录判定所需且经过审核的状态，例如“存在本机私钥=true”；不得把秘密或整份对象 dump 到消息中 |

错误码是排障入口，中文消息供人阅读，结构化字段供筛选和关联；不得只写“失败了”或只写底层异常而没有稳定错误码。

## 级别规则

- `info`：操作开始、关键阶段、路径选择、成功、用户取消、后台跳过和恢复完成。
- `warning`：可恢复的异常、重试、回退路径、外部服务暂不可用但操作仍继续。
- `error`：操作最终失败、数据一致性无法确认或恢复动作失败；必须附错误码和可用的底层诊断。
- 预期中的空列表、未安装、用户尚未配置等正常状态不记为错误。

## 开发者排查顺序

1. 先看导出文件头，确认 Seal 版本和 CI 构建号；旧构建日志不能用于判断新代码是否生效。
2. 用失败卡片中的错误码与发生时间定位本轮操作，确认操作入口、触发来源和最后一个成功阶段。
3. 沿同一 `operationID` 查看开始、阶段、外部边界、重试和最终结果；沿 `diagnosticID` 查看同一次失败的完整脱敏原因。
4. 先按第一处失败判定根因，不从后续级联错误倒推；区分代码/数据错误与网络、Apple 服务、设备通道等外部暂态。
5. 需要复现时，只补充操作步骤、设备 iOS 版本和预期/实际结果；不要求用户发送密码、证书、配对文件或原始账号资料。

## 当前实现与迁移要求

当前日志已有北京时间、构建标识、类别/级别、稳定错误码、环形保留最近 1000 条、写入/读取/导出脱敏、文件 App 镜像和签名/续签轮次卡片。日志页现有“开发者排障”提示说明如何复制错误码和导出日志。

现有 `SealLogEntry` 仍以文本消息为主，轮次视图依赖消息标记；`ImportFailure` 的 `diagnosticID` 尚未贯穿所有日志行。后续按链路增量接入 `operationID`、阶段、耗时、结果和 `diagnosticID`，先从导入/签名/安装/续签主链开始。迁移期间保留旧文本格式可读性；不一次性改写所有调用点，也不为了满足字段而记录无意义事件。

日志本地保存并由用户主动导出。容量达到上限时滚动丢弃最旧事件并在导出头部说明；清空由用户确认。新增日志字段必须同时有脱敏测试、历史 JSON 兼容测试，以及至少一条能证明真实导出内容的测试。
